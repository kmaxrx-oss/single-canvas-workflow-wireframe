1. Intake / Search

DEMO ONLY

Enter trip parameters. This writes searchParams and triggers a mock filter that populates the Results Grid.

This is a client-side mock. No real inventory service. Search only filters the 5 hotels in data/mock-items.json.
Section Contract — Intake / Search
purpose
Capture destination, dates, and guest count to drive relevant results and set initial context for the entire booking flow.
user decision
Does the search surface match what I expect for my trip? Do I have enough control to refine before seeing inventory?
primary action
Search / Update results (writes searchParams)
state reads
[]
state writes
searchParams
mock source
Client-side mock-items.json + simple filter on city/name. No real inventory service.
proof condition
User can enter destination + dates + guests and trigger an action that visibly updates the Results Grid below.
seo / schema notes
Search form should be crawlable. Consider HotelSearch or LodgingReservation schema on the real page.

2. Results Grid

DEMO ONLY

Scannable hotel options. Selecting a card writes selectedHotelId, scrolls to Detail, and highlights the choice.

Section Contract — Results Grid
purpose
Present a scannable, filterable set of hotel options with clear price, rating, and key value props.
user decision
Which property best fits my needs, budget, and location preferences?
primary action
Select hotel → writes selectedHotelId and focuses Detail/Selection
state reads
searchParams, filteredHotelIds
state writes
selectedHotelId
mock source
mock-items.json filtered client-side. Thumbnails are deterministic picsum seeds.
proof condition
Clicking "Select & View" on a card sets selectedHotelId in Demo State, scrolls/focuses the Detail section, and the Detail surface reflects the choice.
seo / schema notes
Each result card should map to a potential real hotel detail URL. ItemList + Hotel structured data in production.

DEMO ONLY

selectedRoomId

4. Checkout Preview / Operation-State Stub

DEMO ONLY

Live summary of selections + a stub for the operation state machine (cart valid, payment pending, failed, confirmed, etc.). No real checkout occurs.

Section Contract — Checkout Preview / Operation-State Stub
purpose
Summarize the committed selections before the real payment/guest details step. Also acts as a stub for operation state machine.
user decision
Are my selections correct? What is the current operational status of this booking intent?
primary action
Simulate operation transitions (writes currentOperationState). No real payment or confirmation.
state reads
selectedHotelId, selectedRoomId, searchParams
state writes
currentOperationState
mock source
Purely derived from current demo state + hard-coded operation state transitions. No backend.
proof condition
The summary shows live hotel + room + dates. Buttons that call setOperationState visibly change the currentOperationState badge and log the transition in the Demo State panel.
seo / schema notes
ReservationPending or potential for Order + Reservation schema. Mark as demo-only in production.
